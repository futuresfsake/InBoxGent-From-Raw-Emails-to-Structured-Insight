# Reproducibility and MLOps

The goal: any number in the report can be regenerated by a reviewer from a fresh clone, and every result can be traced to code, data, configuration and random seed.

## 1. Environment
- Python version pinned in `pyproject.toml` and `.python-version`.
- Dependencies locked (`uv.lock` or `requirements.lock`); upgrades are deliberate commits.
- Setup documented in the README and tested on a clean machine at M0 and M8.

## 2. Configuration
- A single typed configuration (pydantic settings) loaded from `config/*.yaml` and environment variables.
- Contains paths, sample size, seeds, thresholds (dedup, cleaning), model identifiers, prompt versions, budget caps.
- The resolved configuration is hashed and logged at the start of every run.

## 3. Randomness and determinism
- One master seed in configuration, derived per component (`sampling`, `splits`, `models`, `bootstrap`).
- Bootstrap and permutation routines take explicit generators.
- LLM calls use temperature 0 and pinned model identifiers; responses are cached by hash of (model id, prompt version, input text). Note that temperature 0 reduces but does not eliminate nondeterminism, so the cache is the source of reproducibility.
- Model deprecations are a known risk: raw LLM responses used in reported results are archived with their metadata.

## 4. Data versioning and lineage
- **Manifest:** file count, total bytes and content hash of the raw corpus (DE-01).
- **Stage artifacts:** each Parquet carries metadata: stage name, input hashes, code version (git SHA), config hash, row count, creation time.
- **Gold set:** `data/labeled/` holds labels and message ids with a `text_version` field and the SHA-256 of the annotated text, so drift in cleaning is detected immediately.
- **Test lock:** SHA-256 of the sorted test message ids committed before tuning begins.

## 5. Pipeline orchestration
- A `Makefile` target per stage (`make ingest`, `make parse`, `make clean`, `make thread`, `make features`, `make extract`, `make evaluate`, `make train`, `make report`).
- Each stage is idempotent and skips if its inputs and config hash are unchanged.
- Stages are runnable as a CLI: `python -m inboxgent <stage>`.

## 6. Data-quality gates
Run automatically at the end of each stage (pandera schemas plus checks):
- Schema and dtypes
- Uniqueness of identifiers
- Date range sanity and parse-failure rate under threshold
- Null-rate thresholds per column
- Distribution drift checks between stages (e.g., body length before and after cleaning)
- Duplicate-cluster consistency (every duplicate cluster has exactly one canonical message)

A failed gate stops the pipeline and writes a report.

## 7. Experiment tracking
- MLflow with a local file store (`mlruns/`, git-ignored).
- Each run logs: parameters, config hash, data manifest hash, git SHA, metrics with CIs, artifacts (plots, predictions, error tables).
- Run IDs are referenced in `reports/findings.md` next to each figure and table.
- Final metrics tables are exported to `reports/tables/` as CSV and committed.

## 8. Notebook policy
- One question per notebook; each begins with the question and ends with a conclusion.
- Notebooks paired with `.py` files via `jupytext`; outputs stripped with `nbstripout` before commit so no email text leaks.
- A fast fixture run executes notebooks in CI to ensure they run top to bottom.

## 9. Continuous integration
GitHub Actions on every push:
1. Install from lock file
2. Lint (ruff) and type check selected modules (mypy)
3. Run unit tests with coverage
4. Run the end-to-end pipeline on the committed synthetic fixture dataset
5. Run secret scanning

## 10. Release practice
- Tag at the end of each milestone (`v0.1-m1`, ..., `v1.0`).
- A changelog entry per milestone.
- The final release includes the findings report, model card, datasheet and a frozen copy of all result tables.

## 11. Cost and safety controls
- Hard budget cap enforced in the LLM client; spend logged per run.
- Dry-run mode estimates tokens and cost before any paid call.
- Pre-commit blocks files over a size threshold and anything under `data/raw`, `data/interim` or `data/outputs`.

## 12. Reproducibility checklist for release
- [ ] Fresh clone installs from lock file
- [ ] `make all` reproduces reported tables within tolerance
- [ ] Every figure cites a run ID
- [ ] Test-id hash unchanged since lock
- [ ] No text from emails in committed files
- [ ] Model card and datasheet complete
